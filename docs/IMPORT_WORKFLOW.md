# Массовый импорт задач

Этот файл описывает рабочий процесс для архивов вроде турнира Колмогорова,
IMO и IMO Shortlist.

## Журнал импорта

Каждый проход по источнику фиксируется в `data/import_batches/*.yaml`.
Журнал не является карточкой задачи. Он отвечает на вопросы:

- какие источники были просмотрены;
- какие задачи стали кандидатами;
- что уже добавлено в базу;
- что оказалось дубликатом;
- что пропущено и почему;
- какие задачи требуют ручной проверки.

Статусы элементов:

- `candidate` — найден кандидат, карточка ещё не создана;
- `added` — карточка создана, поле `problem_id` обязательно;
- `duplicate` — это уже существующая карточка или переформулировка;
- `skipped` — задача не подходит базе;
- `needs_review` / `needs_human_review` — не хватает уверенности.

## Профиль задачи

У новых карточек желательно заполнять `problem_profile`. Это навигационный слой,
который помогает искать родственные задачи, когда одних меток уже мало.

Рекомендуемые поля:

- `objects`: основные объекты, например `grid`, `bipartite_graph`, `tournament`;
- `methods`: методы решения, например `double_counting`, `longest_path`;
- `transformations`: переходы, например `complement_graph`, `auxiliary_graph`;
- `goal`: тип цели, например `existence`, `minimum_attempts`, `edge_bound`;
- `auxiliary_graph_type`: тип вспомогательного графа, особенно если граф появляется только в решении;
- `invariants`: чётность, связность, степень, раскраска и т.п.;
- `keywords`: короткие свободные ключи для поиска;
- `status`: статус проверки профиля.

Профиль не заменяет `tags` и `standard_idea_ids`. Он нужен для более тонкого
поиска связей: например, две задачи могут обе использовать лес, но в одной лес
является условием, а в другой возникает как граф сравнений в решении. Для второго
случая верхняя навигационная метка — `graph_in_solution`; `graph_model` оставляем
для самостоятельной графовой модели или эквивалентной графовой переформулировки.

## Добавление задач из архива

1. Создать или обновить import batch.
2. Для каждой найденной задачи проверить официальный или устойчивый источник.
3. Если в источнике указан первоисточник или переиздание (например, `MEMO 2021 I-2`),
   сохранить канонический внешний номер в карточке: `memo_2021_i2` в
   `problem_profile.keywords`, либо явным текстом в `editorial.notes` / `sources`.
   Такой номер нельзя оставлять только в сыром архивном файле: иначе поиск связей его не увидит.
4. Проверить дубликаты:
   `python tools/search.py query "ключевые слова задачи"`
   Для задач с внешним номером дополнительно запустить:
   `python tools/source_collisions.py --problem <id>`
5. Создать карточку только для опубликованной задачи. Если полное решение уже
   найдено, перенести его в карточку как полноценное русское доказательство. Если
   полного решения пока нет или есть только внешний текст, который не успели
   перенести, создать карточку без решений: `solutions: []`.
6. Если графовая задача является перепечаткой другой графовой задачи, обе карточки
   должны быть в `data/problems` и должны получить связь `reprint` расстояния 1.
   Если первоисточник найден только в extracted-архиве и тоже является графовым,
   сначала добавить карточку первоисточника. Если первоисточник неграфовый, перепечатку
   не добавлять в графовую базу; import item пометить `skipped` или `duplicate`
   с причиной `original_not_graph`.
7. Заполнить оригинальную формулировку и графовую формулировку, если она
   является самостоятельной и эквивалентной.
8. Заполнить `problem_profile`, `tags`, `standard_idea_ids`. Если граф только в решении, поставить `kind.secondary: graph_in_solution`, заполнить `editorial.graph_theory_absent_reason` и использовать тег `graph_in_solution` вместо `graph_model`.
9. Запустить:
   `python tools/suggest_relations.py --problem <id>`
10. Добавить только те связи, для которых есть содержательный текст.
11. Обновить import batch: `added`, `duplicate`, `skipped` или `needs_review`.
12. Запустить `validate`, `check_links`, `build_index`, `build_viewer`.

## Правило для решений при импорте

Новые задачи нельзя импортировать с частичными решениями. Для `solutions[]` действует
режим "всё или ничего":

- если решение добавляется, оно должно быть полным, самодостаточным и написанным
  на русском языке;
- внешний источник, PDF, скан, архив или форумная ссылка не заменяют текст решения
  внутри карточки;
- план решения, outline, proof sketch, сжатый пересказ, машинная выжимка и текст
  вида "официальное решение делает X, затем Y" не помещаются в `solutions[]`;
- если полное решение есть во внешнем источнике, его нужно перенести и перевести
  перед добавлением в `solutions[]`;
- если полного русского текста пока нет, оставить `solutions: []`, а найденную
  идею, ссылку и состояние работы зафиксировать в `ideas[]`, `sources[]`,
  `editorial.notes` или import batch.

Если решение в источнике существенно опирается на рисунок, таблицу, сетку,
геометрическую схему или серию локальных модификаций, перенос должен включать эту
визуальную часть. Не надо насильно заменять удобную схему длинным координатным
описанием только ради текстовости. Но картинка должна быть локальной и проверенной:
в карточке нужно указать, какие элементы на ней важны, какие случаи она покрывает,
и почему из неё однозначно следует соответствующий шаг решения.

Для таких карточек пустой `solutions[]` считается корректным промежуточным
состоянием. Неполный элемент внутри `solutions[]` считается ошибкой импорта и должен
быть либо дописан до полного решения, либо удалён из `solutions[]`.

## Раздельные связи

Основной файл `data/relations/relations.yaml` остаётся рабочим.
Для больших новых проходов можно складывать связи в
`data/relations/relations.d/<batch-or-topic>.yaml`.
Инструменты читают оба места и проверяют уникальность `id`.
