# AI Card Rules

Короткий свод правил для ИИ, который добавляет или редактирует карточки базы.
Цель: не положить в базу правдоподобную ошибку. Если кусок трудный, честно
пометь его и вынеси в отдельную проверку.

## 0. Быстрый Вход

Источник истины: `data/`.

Производные файлы: `viewer/index.html`, `docs/index.html`,
`index/generated.sqlite`, `viewer/assets/`, `docs/assets/`. Их пересобирают,
но не редактируют как данные.

Перед правками:

```powershell
git status --short
python tools\validate.py
python tools\check_links.py
python tools\comments.py --status open
```

Для поиска:

```powershell
python tools\search.py query "ключевые слова"
python tools\search.py problem <problem_id>
python tools\search.py neighbors <problem_id> --depth 2
python tools\suggest_relations.py --problem <problem_id> --limit 20
python tools\source_collisions.py --problem <problem_id>
```

После содержательных правок:

```powershell
python tools\validate.py
python tools\check_links.py
python tools\audit_rules.py
python tools\build_viewer.py --out viewer\index.html
```

`tools\audit_rules.py` даёт редакторские warnings. Это не замена
`validate.py`, а защита от типичных агентских ошибок.

## 1. Формат Файлов

Файлы `*.yaml` в `data/` фактически являются JSON-совместимым YAML:

- пиши валидный JSON;
- используй двойные кавычки;
- не используй YAML-якоря, `|`, комментарии внутри данных, trailing commas;
- кодировка: UTF-8 без BOM;
- LaTeX backslash в строках экранируется дважды: `\\( ... \\)`, `\\[ ... \\]`,
  `\\le`, `\\ge`, `\\sqrt`, а не `\( ... \)` или `\le`.

Если после правки падает `Invalid \escape`, почти всегда в строке есть
одиночный LaTeX-backslash.

## 2. Минимальная Карточка

Карточка задачи обязана иметь:

```text
id
title
statements
ideas
solutions
difficulty
tags
sources
editorial
```

`title` должен быть самодостаточным: по названию видно объект, условие и цель.
Источник можно оставить в конце, если он помогает навигации.

`statements.original` обязателен. `statements.graph_theory` обязателен, кроме
двух честных случаев:

- графовая формулировка совпала с original и удалена как дубликат:
  `editorial.graph_theory_duplicate_removed`;
- граф возникает только в решении:
  `kind.secondary` содержит `graph_in_solution`, а в `editorial` заполнен
  `graph_theory_absent_reason`.

Каждый statement должен иметь `id`, `title`, `text`, `status`,
`self_contained`, `definition_ids`.

## 3. Условия И Переформулировки

Условие нельзя "улучшать" без источника. Любая смена математической силы
требует проверки источника или статуса `needs_human_review`.

Опасные изменения:

- простой граф / мультиграф / ориентированный граф;
- `не более`, `меньше`, `ровно`, `хотя бы`;
- чётность, диапазон `n`, граничные случаи;
- точная константа или ответ;
- `существует` вместо `для любого`;
- путь, цикл, trail, walk, matching, покрытие и независимость.

Graph-theory formulation считается новой теоремой. При переводе сюжета в графы
проверь обе стороны эквивалентности: из исходного условия в графовую модель и
обратно.

`statements.graph_theory` должен быть математической постановкой, а не
рассказом о решении. Запрещённые маркеры:

- "построим граф";
- "официальное решение рассматривает";
- "задача спрашивает";
- "модель присутствует";
- сюжетные слова вроде людей, домов, городов, встреч, если они уже переведены
  в вершины, рёбра, веса, раскраски или пути.

Если две формулировки внутри карточки похожи, но редакционно нужны обе, добавь
в обе `distinct_from`. Если они совпадают по смыслу и источникам, лучше
объединить карточку или оставить одну формулировку.

## 4. Источники

URL живут в `data/sources/sources.yaml`. В карточках используются `source_id`.

У statement можно использовать:

- legacy `source_id`;
- новый `source_ids`, если источников несколько.

В `problem.sources[]` добавляй `statement_ids`, если источник относится только
к отдельной формулировке, а не ко всей карточке.

Если две разные карточки намеренно имеют один и тот же текст условия и тот же
источник, это допустимо только для разных частей или принципиально разных
случаев одной опубликованной задачи. Тогда каждый такой statement обязан иметь:

```json
"shared_statement_group": {
  "id": "source-problem-two-cases",
  "case_id": "case-a",
  "note": "This card treats the first genuinely different case."
}
```

У всех карточек группы общий `id`, но разные `case_id`.

## 5. Решения

Правило: всё или ничего.

`solutions[]` содержит только полноценное русское самодостаточное доказательство.
Если полного доказательства нет, для новой карточки лучше `solutions: []`.

Не класть в `solutions[]`:

- outline, sketch, plan, summary, compressed proof;
- машинный пересказ источника;
- текст вида "автор делает X и получает Y";
- ссылку на внешний PDF, форум, картинку или handout как часть доказательства;
- фразу "аналогично", "стандартно", "легко видеть", если за ней спрятан
  нетривиальный шаг;
- красивую идею без полного proof load.

Если есть только идея, положи её в `ideas[]`, `editorial.notes`, comment или
audit-note, но не повышай до решения.

Если решение держится на отдельной лемме, лемма должна быть доказана в тексте
или вынесена в отдельную карточку со связью `prerequisite`.

`standard_idea_ids` привязываются к конкретному решению, а не к карточке целиком.

`examples` в решении допустимы, включая локальные картинки
`assets/examples/...`, но пример не должен нести скрытый ключевой шаг. Картинка
должна существовать в `data/assets/`, а caption/alt должны объяснять, что на
ней проверяется.

## 6. Статусы

Не повышай статус, если не проверил соответствующий слой.

`public_ready: true` допустим только когда нет локальных `needs_review`,
`needs_human_review` или `disputed` в:

- `editorial.review_status`;
- statement status;
- `self_contained.status`;
- solution status;
- difficulty/profile, если они содержательно важны для карточки.

`ai_checked` не отменяет локальные сомнения. Если хотя бы одна исходная
формулировка или решение требует проверки, карточка не считается полностью
проверенной.

Для трудного места используй явную метку:

```text
status: needs_human_review
review_notes: "Какой именно шаг не проверен и что нужно проверить."
```

или отдельный comment типа `bug_report`, `alternative_solution`,
`related_connection`.

## 7. Родственные Связи

Связь должна иметь содержательный текст в обе стороны:

```text
from
to
type
distance
forward_text
backward_text
status
confidence
```

Не добавляй голую пару id.

Типы не взаимозаменяемы:

- `reformulation`: та же задача в другом языке;
- `reprint`: перепечатка или точный первоисточник;
- `solution_transfer`: решение реально переносится;
- `prerequisite`: результат реально нужен в решении;
- `same_motif`: похожий мотив, но перенос не доказан;
- `paired_variant`: парный вариант, где различие существенно.

Для `same_motif` с `confidence < 0.8` не ставь `ai_checked`. При
`confidence < 0.7` лучше запускать отдельную проверку или оставлять
`needs_human_review`.

Если связь ссылается на конкретное решение, проверь anchors:
`from_solution_id`, `to_solution_id`.

После удаления или объединения карточек все внешние связи должны указывать на
новую основную карточку.

## 8. Объединения И Разделения

Объединяй карточки, если это одна математическая задача:

- разные источники дают одну формулировку;
- есть графовая и олимпиадная формулировки одного утверждения;
- один источник даёт фиксированный параметр, а основная карточка может быть
  параметрической;
- решение действительно одно и то же.

Не объединяй, если различаются ответ, инвариант, конструкция, верхняя/нижняя
оценка или ключевая лемма.

Split-карточки для двух случаев одной задачи держи раздельно. Не переноси теги,
решения и оценки из одного случая в другой "по симметрии" без проверки.

Merged-карточка почти всегда требует отдельного high-reasoning прохода перед
повышением статуса.

## 9. Теги И Профиль

`tags` берутся из закрытого словаря `data/taxonomy/tags.yaml`.

`problem_profile` помогает поиску родства, но не доказывает родство. Особенно
осторожно с `keywords`: там бывают id, snake_case, человеческие фразы и
исторические номера.

При добавлении новой карточки желательно заполнить:

```text
objects
methods
transformations
goal
auxiliary_graph_type
invariants
keywords
status
```

## 10. Эскалация

Агент должен остановиться и не додумывать, если:

- меняется математическая сила условия;
- графовая модель не проверена в обе стороны;
- решение требует новой конструкции;
- ключевая лемма не сформулирована или не доказана;
- источник и карточка расходятся;
- два источника противоречат друг другу;
- перенос решения между задачами не очевиден;
- доказательство зависит от картинки или PDF, которые не перенесены локально;
- рабочее дерево содержит чужие изменения в тех же файлах.

Что сделать вместо догадки:

```text
problem_id#statement_id или problem_id#solution_id
status: hard | borderline | placeholder | skipped
reason: конкретный непроверенный шаг
needed: источник | локальная лемма | рисунок | уточнение условия
action_taken: checked_only | easy_repair | none
next_agent: high_reasoning
```

Для high-reasoning агентов экономь контекст:

- один агент = один узкий scope: одна карточка, одна пара, один bucket;
- не грузить весь `data/problems/`;
- передавать id, путь, конкретный вопрос и критерий pass/fail;
- не использовать полный fork context, если достаточно самодостаточного задания;
- просить короткий отчёт: вывод, риск, файлы, что проверено, что не проверено.

## 11. Минимальный Финальный Чек

После правок, которые меняют данные:

```powershell
python -m py_compile tools\validate.py tools\audit_rules.py tools\lib.py
python tools\validate.py
python tools\check_links.py
python tools\audit_rules.py --max-items 10
```

Если менялись данные, которые видит пользователь:

```powershell
python tools\build_viewer.py --out viewer\index.html
```

Если менялись связи или источники:

```powershell
python tools\source_collisions.py --json
python tools\search.py neighbors <problem_id> --depth 2
```

Главное правило: лучше честная метка `needs_human_review` и отдельный hard-case
аудит, чем красивое неверное улучшение.
